## 1. Общее описание

Модуль `mqtt_subscribe.c` реализует обработку входящих MQTT-сообщений (команд и настроек) контроллера установки обратного осмоса. Он отвечает за:

- **Подписку** на набор командных и конфигурационных топиков при подключении к брокеру.
- **Диспетчеризацию** входящих сообщений по соответствующим обработчикам на основе имени топика.
- **Управление режимом работы** установки через команды режима (start_auto, stop, и т.д.).
- **Ручное управление** дискретными выходами (помпы, ТЭН) в режиме MANUAL.
- **Управление дозатором** -- включение/выключение.
- **Удалённое изменение настроек** (уставки давления, дозатора, промывки, таймаутов) через JSON-сообщения.

Все объявления функций данного модуля находятся в `mqtt_app.c` как `extern`-прототипы (отдельного заголовочного файла для subscribe нет).

## 4. Структура MQTT-топиков (подписка)

### 4.1. Полный список подписок

При подключении к брокеру вызывается `mqtt_subscribe_all`, которая подписывается на следующие топики:

| # | Топик | QoS | Обработчик | Описание |
|---|-------|-----|------------|----------|
| 1 | `ro_plant/command/mode` | 1 | `handle_mode` | Команды управления режимом работы |
| 2 | `ro_plant/command/pump` | 1 | `handle_pump` | Ручное управление дискретными выходами (помпами) |
| 3 | `ro_plant/command/doser` | 1 | `handle_doser` | Включение/выключение дозатора |
| 4 | `ro_plant/command/heater` | 1 | `handle_heater` | Управление нагревателем (ТЭН) |
| 5 | `ro_plant/settings/#` | 1 | `handle_settings` | Wildcard-подписка на все секции настроек |

**Примечание:** подписка `ro_plant/settings/#` покрывает все поддтопики вида `ro_plant/settings/<section>`, где `<section>` -- имя секции конфигурации.

## 5. Функции

### 5.1. Публичные функции (вызываются из mqtt_app.c)

---

#### `mqtt_subscribe_all`

```c
void mqtt_subscribe_all(esp_mqtt_client_handle_t client);
```

**Описание:**
Подписывается на все командные и конфигурационные MQTT-топики. Вызывается из обработчика события `MQTT_EVENT_CONNECTED` в `mqtt_app.c`.

**Параметры:**

| Параметр | Тип | Описание |
|----------|-----|----------|
| `client` | `esp_mqtt_client_handle_t` | Хендл активного MQTT-клиента |

**Возвращаемое значение:** нет (`void`).

**Подписки:** см. таблицу в разделе 4.1.

---

#### `mqtt_subscribe_handle_message`

```c
void mqtt_subscribe_handle_message(const char *topic, int topic_len,
                                    const char *data, int data_len);
```

**Описание:**
Диспетчер входящих MQTT-сообщений. Вызывается из обработчика события `MQTT_EVENT_DATA` в `mqtt_app.c`. Определяет, какому топику соответствует сообщение, и перенаправляет в соответствующий внутренний обработчик.

**Параметры:**

| Параметр | Тип | Описание |
|----------|-----|----------|
| `topic` | `const char *` | Указатель на строку топика (не null-terminated!) |
| `topic_len` | `int` | Длина строки топика в байтах |
| `data` | `const char *` | Указатель на payload сообщения (не null-terminated!) |
| `data_len` | `int` | Длина payload в байтах |

**Возвращаемое значение:** нет (`void`).

**Логика маршрутизации:**

| Условие | Вызываемый обработчик |
|---------|-----------------------|
| Топик начинается с `"ro_plant/command/mode"` (длина >= 24) | `handle_mode(data, data_len)` |
| Топик начинается с `"ro_plant/command/pump"` (длина >= 24) | `handle_pump(data, data_len)` |
| Топик начинается с `"ro_plant/command/doser"` (длина >= 25) | `handle_doser(data, data_len)` |
| Топик начинается с `"ro_plant/command/heater"` (длина >= 26) | `handle_heater(data, data_len)` |
| Топик начинается с `"ro_plant/settings/"` (длина > 18) | `handle_settings(topic + 18, topic_len - 18, data, data_len)` |

### 5.2. Статические функции (внутренние обработчики)

---

#### `handle_mode`

```c
static void handle_mode(const char *payload, int len);
```

**Описание:**
Обработчик команд режима работы установки. Сравнивает текстовое содержимое payload с набором известных команд и отправляет соответствующую команду в машину состояний.

**Параметры:**

| Параметр | Тип | Описание |
|----------|-----|----------|
| `payload` | `const char *` | Текст команды (не null-terminated) |
| `len` | `int` | Длина текста команды |

**Возвращаемое значение:** нет (`void`).

**Формат payload:** простая текстовая строка (не JSON).

**Поддерживаемые команды:**

| Payload (текст) | Команда SM | Описание |
|------------------|------------|----------|
| `start_auto` | `CMD_START_AUTO` | Запуск автоматического режима работы установки |
| `stop` | `CMD_STOP` | Остановка установки (переход в IDLE) |
| `start_washing` | `CMD_START_WASHING` | Запуск цикла промывки мембран |
| `confirm_wash` | `CMD_CONFIRM_WASH_PHASE` | Подтверждение перехода к следующей фазе промывки |
| `set_manual` | `CMD_SET_MANUAL` | Перевод в ручной режим управления |
| `reset_fault` | `CMD_RESET_FAULT` | Сброс аварии, возврат из состояния FAULT |

**Поведение:** если payload не соответствует ни одной известной команде, сообщение игнорируется без логирования (команда остаётся `CMD_NONE`).

---

#### `handle_pump`

```c
static void handle_pump(const char *data, int len);
```

**Описание:**
Обработчик команды ручного управления дискретными выходами (помпами). Работает **только в режиме MANUAL** -- в других режимах команда игнорируется с предупреждением в лог.

**Параметры:**

| Параметр | Тип | Описание |
|----------|-----|----------|
| `data` | `const char *` | JSON-строка с командой (не null-terminated) |
| `len` | `int` | Длина JSON-строки |

**Возвращаемое значение:** нет (`void`).

**Формат payload (JSON):**

```json
{
  "mask": <uint8_t>
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `mask` | число (0-255) | Битовая маска дискретных выходов. Каждый бит соответствует одному DO. Маска устанавливается целиком, перезаписывая текущее состояние всех выходов. |

**Пример:**
```json
{"mask": 5}
```
Установит DO1 (бит 0) и DO3 (бит 2) в состояние ON, все остальные -- OFF.

**Условие выполнения:** `state_machine_get_state() == SM_MANUAL`. При невыполнении -- предупреждение в лог, команда игнорируется.

**Вызываемая функция:** `state_machine_manual_set_do(mask)`.

---

#### `handle_doser`

```c
static void handle_doser(const char *data, int len);
```

**Описание:**
Обработчик команды управления дозатором (антискалант / химический реагент). Включает или выключает дозатор.

**Параметры:**

| Параметр | Тип | Описание |
|----------|-----|----------|
| `data` | `const char *` | JSON-строка с командой (не null-terminated) |
| `len` | `int` | Длина JSON-строки |

**Возвращаемое значение:** нет (`void`).

**Формат payload (JSON):**

```json
{
  "enabled": <bool>
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `enabled` | bool (`true`/`false`) | `true` -- включить дозатор, `false` -- выключить |

**Пример:**
```json
{"enabled": true}
```

**Вызываемая функция:** `doser_enable(en)`.

**Примечание:** в отличие от `handle_pump` и `handle_heater`, эта команда **не проверяет текущий режим** работы -- дозатор можно включить/выключить из любого состояния.

---

#### `handle_heater`

```c
static void handle_heater(const char *data, int len);
```

**Описание:**
Обработчик команды управления нагревательным элементом (ТЭН). Работает **только в режиме MANUAL**. Управляет одним конкретным дискретным выходом (DO4, бит 3), не затрагивая остальные выходы.

**Параметры:**

| Параметр | Тип | Описание |
|----------|-----|----------|
| `data` | `const char *` | JSON-строка с командой (не null-terminated) |
| `len` | `int` | Длина JSON-строки |

**Возвращаемое значение:** нет (`void`).

**Формат payload (JSON):**

```json
{
  "on": <bool>
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `on` | bool (`true`/`false`) | `true` -- включить ТЭН, `false` -- выключить |

**Пример:**
```json
{"on": true}
```

**Логика работы:**
1. Проверяет, что текущий режим `SM_MANUAL`. Если нет -- предупреждение в лог, команда игнорируется.
2. Читает текущее состояние дискретных выходов через `hal_gpio_read_do_state()`.
3. Устанавливает или сбрасывает бит 3 (DO4 = ТЭН):
   - `on: true` -> `cur |= (1 << 3)` (установить бит)
   - `on: false` -> `cur &= ~(1 << 3)` (сбросить бит)
4. Записывает обновлённую маску через `state_machine_manual_set_do(cur)`.

**Важно:** в отличие от `handle_pump`, `handle_heater` модифицирует только один бит (DO4), сохраняя состояние всех остальных выходов. `handle_pump` же перезаписывает маску целиком.

---

#### `handle_settings`

```c
static void handle_settings(const char *section, int section_len,
                             const char *data, int data_len);
```

**Описание:**
Обработчик сообщений настроек. Обрабатывает топики вида `ro_plant/settings/<section>`, где `<section>` определяет секцию конфигурации. Парсит JSON-payload и обновляет соответствующие параметры через `config_manager`.

**Параметры:**

| Параметр | Тип | Описание |
|----------|-----|----------|
| `section` | `const char *` | Имя секции (извлечённое из топика, не null-terminated) |
| `section_len` | `int` | Длина имени секции |
| `data` | `const char *` | JSON-строка с новыми значениями (не null-terminated) |
| `data_len` | `int` | Длина JSON-строки |

**Возвращаемое значение:** нет (`void`).

**Ограничения буферов:**
- `section` копируется в буфер 32 байта (обрезается до 31 символа).
- `data` копируется в буфер 256 байт (обрезается до 255 символов).

### Поддерживаемые секции настроек

#### 5.2.1. Секция `pressure`

**Топик:** `ro_plant/settings/pressure`

**Формат payload (JSON):**

```json
{
  "p1_max": <float>,
  "p3_max": <float>,
  "p4_max": <float>,
  "filter_dp_warn": <float>
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `p1_max` | float | Максимально допустимое давление на датчике P1 |
| `p3_max` | float | Максимально допустимое давление на датчике P3 |
| `p4_max` | float | Максимально допустимое давление на датчике P4 |
| `filter_dp_warn` | float | Порог предупреждения о перепаде давления на фильтре |

**Примечание:** все поля опциональны -- можно передать только те, которые нужно изменить. Остальные останутся без изменений (читаются из текущей конфигурации).

## 7. Особенности реализации

### Буферизация строк
Все входящие данные (topic, data) от ESP-IDF MQTT клиента приходят **без нулевого терминатора**. Каждый обработчик копирует payload в локальный буфер и добавляет `'\0'` перед парсингом:
- `handle_pump`, `handle_doser`, `handle_heater`: буфер 64 байта.
- `handle_settings`: буфер section 32 байта, буфер data 256 байт.

### Безопасность JSON-парсинга
- Если `cJSON_Parse` возвращает `NULL` -- обработчик завершается без действий.
- Каждое поле проверяется на наличие (`cJSON_GetObjectItem`) и правильный тип (`cJSON_IsNumber`, `cJSON_IsBool`) перед использованием.
- `cJSON_Delete(root)` вызывается после обработки для освобождения памяти.

### Паттерн чтения-изменения-записи настроек
Для секций настроек используется паттерн:
1. Прочитать текущую конфигурацию: `cfg = config_manager_get()->section`.
2. Обновить только те поля, которые присутствуют в JSON.
3. Записать обратно: `config_manager_set_section(&cfg)`.

Это позволяет отправлять в JSON только изменяемые поля, а не всю секцию целиком.
