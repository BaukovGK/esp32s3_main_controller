# web_api_status.c — GET-обработчики REST API статусов, конфигурации, аварий и диагностики

## Описание файла

Модуль `web_api_status` реализует все GET-обработчики REST API контроллера обратного осмоса. Через эти эндпоинты веб-интерфейс (или внешний клиент) может получать:

- Полный текущий статус системы (состояние конечного автомата, DI/DO, блокировки, дозатор, аналоговые входы, расходомеры, кондуктометры, телеметрия, uptime)
- Текущую конфигурацию всех подсистем
- Статус MQTT-подключения
- Активные и исторические аварии
- Диагностическую информацию (память, стеки задач, статус Modbus)

Все ответы возвращаются в формате JSON.

Модуль не имеет собственного заголовочного файла — его единственная публичная функция `web_api_register_status()` объявлена как forward-declaration в `web_server.c`.

**Файл реализации:** `components/web_server/web_api_status.c`

### `static void add_float_or_null(cJSON *obj, const char *name, float val)`

**Область видимости:** внутренняя (static)

**Параметры:**

| Параметр | Тип | Описание |
|----------|-----|----------|
| `obj` | `cJSON *` | JSON-объект, в который добавляется поле |
| `name` | `const char *` | Имя добавляемого поля |
| `val` | `float` | Значение для добавления |

**Возвращаемое значение:** нет (`void`)

**Описание:**

Вспомогательная функция для безопасного добавления числа с плавающей точкой в JSON-объект. Если значение `val` является NaN (`isnan(val)` == true), добавляет `null` вместо числа. Это предотвращает генерацию невалидного JSON с `NaN`, который не является допустимым значением в стандарте JSON.

### `static esp_err_t status_get_handler(httpd_req_t *req)`

**Область видимости:** внутренняя (static)
**URI:** `GET /api/v1/status`

**Параметры:**

| Параметр | Тип | Описание |
|----------|-----|----------|
| `req` | `httpd_req_t *` | Указатель на структуру HTTP-запроса |

**Возвращаемое значение:**
- `ESP_OK` — успех
- `ESP_FAIL` — ошибка выделения памяти для JSON

**Описание:**

Основной обработчик, возвращающий полный текущий статус системы в формате JSON. Формирует обширный JSON-объект, включающий все подсистемы.

**Структура JSON-ответа:**

```json
{
  "state": "IDLE|AUTO|WASHING|MANUAL|FAULT",
  "auto_sub": "STARTING_PUMP1|...|STOPPING" | null,
  "wash_sub": "HEATING|SUPPLY|DRAIN|DONE" | null,
  "fault_flags": <число>,
  "di": <число>,
  "do": <число>,
  "interlocks": {
    "flags": <число>,
    "estop": true|false,
    "filter_warn": true|false,
    "allow": [<pump_feed>, <pump_stage1>, <pump_stage2>, <heater>, <doser>]
  },
  "doser": {
    "state": "OFF|RUNNING|PAUSE",
    "enabled": true|false
  },
  "analog": [
    {"name": "P1|P2|P3|P4|T", "value": <float>|null, "unit": "bar|C", "fault": true|false}
  ],
  "flow": [
    {"name": "Q1|Q2|Q3|Q4", "flow": <float>|null, "volume": <float>|null, "ok": true|false}
  ],
  "cond": [
    {"name": "σ1|σ2|σ3", "value": <float>|null, "temp": <float>|null, "ok": true|false}
  ],
  "telemetry": {
    "filter_dp": <float>|null,
    "stage1_feed": <float>|null,
    "recovery2": <float>|null,
    "recovery_sys": <float>|null,
    "sel1": <float>|null,
    "sel2": <float>|null
  },
  "uptime_s": <число>
}
```

**Подробное описание формирования ответа:**

1. **Состояние КА:** Получает `sm_status_t` через `state_machine_get_status()`. Добавляет строковое состояние, подсостояние AUTO (или null), подсостояние WASHING (или null), флаги аварий.

2. **DI/DO:** Считывает текущие значения дискретных входов (`hal_gpio_read_di()`) и выходов (`hal_gpio_read_do_state()`) как числа (битовые маски).

3. **Блокировки:** Вызывает `interlocks_check()` и формирует объект с флагами, E-STOP, предупреждением фильтра и массивом разрешений (подающий насос, насос 1-й ступени, насос 2-й ступени, нагреватель, дозатор).

4. **Дозатор:** Получает состояние и флаг включённости.

5. **Аналоговые входы (5 каналов):** P1, P2, P3, P4 (давления, бар) и T (температура, Цельсий). Для каждого канала — имя, значение (или null при NaN), единица измерения, флаг неисправности.

6. **Расходомеры (4 канала):** Q1-Q4. Для каждого — имя, мгновенный расход (м3/ч), накопленный объём (м3), статус работоспособности.

7. **Кондуктометры (3 канала):** sigma1-sigma3. Для каждого — имя, электропроводность (мкСм), температура (Цельсий), статус.

8. **Телеметрия:** Вычисляемые параметры — перепад давления на фильтре, расход подачи 1-й ступени, рекавери 2-й ступени, системный рекавери, селективность 1-й и 2-й ступеней.

9. **Uptime:** Время работы в секундах, вычисленное из `esp_timer_get_time()`.

10. **Отправка:** Сериализует JSON в строку (`cJSON_PrintUnformatted`), отправляет как `application/json`, затем освобождает память строки и JSON-дерева.

### `static esp_err_t config_get_handler(httpd_req_t *req)`

**Область видимости:** внутренняя (static)
**URI:** `GET /api/v1/config`

**Параметры:**

| Параметр | Тип | Описание |
|----------|-----|----------|
| `req` | `httpd_req_t *` | Указатель на структуру HTTP-запроса |

**Возвращаемое значение:** `ESP_OK`

**Описание:**

Возвращает полную текущую конфигурацию системы в формате JSON. Получает указатель на конфигурацию через `config_manager_get()`.

**Структура JSON-ответа:**

```json
{
  "pressure": {
    "p1_max": <float>,
    "p3_max": <float>,
    "p4_max": <float>,
    "filter_dp_warn": <float>
  },
  "doser": {
    "run_time_min": <int>,
    "cycle_time_min": <int>
  },
  "washing": {
    "target_temp_C": <float>,
    "max_temp_C": <float>,
    "t_overshoot_C": <float>
  },
  "timeouts": {
    "pump_confirm_ms": <int>,
    "pump_ramp_ms": <int>
  },
  "mqtt": {
    "broker_uri": "<строка>",
    "username": "<строка>",
    "password": "<строка>",
    "client_id": "<строка>",
    "publish_interval_s": <int>,
    "enabled": <int 0|1>
  }
}
```

**Секции конфигурации:**

- **pressure** — пороговые значения давлений (p1_max, p3_max, p4_max в барах, filter_dp_warn — порог предупреждения перепада давления на фильтре)
- **doser** — параметры дозатора (время работы, время цикла в минутах)
- **washing** — параметры промывки (целевая температура, максимальная температура, допустимый перегрев в градусах Цельсия)
- **timeouts** — таймауты (подтверждение запуска насоса, время разгона в миллисекундах)
- **mqtt** — параметры MQTT-подключения (URI брокера, логин, пароль, ID клиента, интервал публикации, флаг включения)

### `static esp_err_t alarms_get_handler(httpd_req_t *req)`

**Область видимости:** внутренняя (static)
**URI:** `GET /api/v1/alarms`

**Параметры:**

| Параметр | Тип | Описание |
|----------|-----|----------|
| `req` | `httpd_req_t *` | Указатель на структуру HTTP-запроса |

**Возвращаемое значение:** `ESP_OK`

**Описание:**

Возвращает информацию об авариях системы: активные аварии и историю.

**Структура JSON-ответа:**

```json
{
  "active": [
    {
      "id": <число>,
      "ts": <число, секунды>,
      "cat": "<категория>",
      "code": "<код>",
      "value": <число>
    }
  ],
  "history": [
    {
      "id": <число>,
      "ts": <число, секунды>,
      "cat": "<категория>",
      "code": "<код>",
      "active": true|false
    }
  ]
}
```

**Описание полей:**

- **active** — массив активных аварий (до 16 штук):
  - `id` — уникальный идентификатор аварии
  - `ts` — временная метка в секундах (конвертируется из микросекунд)
  - `cat` — строковая категория аварии (через `alarm_category_str()`)
  - `code` — строковый код аварии (через `alarm_code_str()`)
  - `value` — числовое значение, связанное с аварией

- **history** — массив последних записей истории аварий (до 16 штук):
  - Те же поля + `active` — флаг, активна ли авария в данный момент

### `static esp_err_t diagnostics_get_handler(httpd_req_t *req)`

**Область видимости:** внутренняя (static)

**Параметры:**

| Параметр | Тип | Описание |

**Возвращаемое значение:** `ESP_OK`

**Описание:**

Возвращает диагностическую информацию о системе. Вызывает `diagnostics_collect(&diag)` для сбора данных.

**Структура JSON-ответа:**

```json
{
  "heap_free": <число>,
  "heap_min": <число>,
  "uptime_s": <число>,
  "stack": {
    "<имя_задачи>": <свободный_стек>,
```

- `modbus.errors` — массив счётчиков ошибок для 4 Modbus-устройств

## Архитектурные замечания

- Обработчик `/api/v1/status` собирает данные из **12 различных модулей**, что делает его наиболее ресурсоёмким эндпоинтом. Сериализация в JSON с помощью cJSON требует динамического выделения памяти.
- Все float-значения проверяются на NaN перед добавлением в JSON через `add_float_or_null()` — это обеспечивает валидность JSON-ответа.
- Обработчик MQTT-статуса использует ручное формирование JSON (через `snprintf`) вместо cJSON для минимизации потребления памяти.
- Подсостояния (auto_sub, wash_sub) добавляются в ответ только при нахождении в соответствующем состоянии, иначе устанавливаются в `null`.
- Массивы аварий ограничены 16 элементами, что является компромиссом между полнотой информации и размером ответа.
